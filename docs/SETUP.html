Connection guide

Set up Maintenance desk

The files are ready for deployment. Your database, website address and verified email sender still need to be connected. No live data or emails are enabled in the supplied package.

Try the sample workspace · Open the connected app

1. Create the shared database

  1. Create a new project at Supabase. Keep its password private.
  2. In SQL Editor, paste and run supabase/schema.sql from the package once. It creates maintenance tables and access rules.
  3. In Authentication settings, disable public sign-ups. Under Authentication → Users, create your administrator email/password user and confirm the account through the dashboard.
  4. Copy that user's UUID and run this SQL, substituting its UUID:
insert into public.pm_members(user_id, role)
values ('YOUR-AUTH-USER-UUID', 'admin');

Create other users the same way. Use editor for people updating records or viewer for read-only access. Only administrators manage recipients. One project serves one maintenance workspace.

2. Connect the website

Open docs/config.js in a text editor. Enter your project's URL and PUBLIC publishable key from its settings:

window.MAINTENANCE_CONFIG = {
  supabaseUrl: 'https://YOUR-PROJECT.supabase.co',
  publishableKey: 'YOUR-PUBLIC-PUBLISHABLE-KEY',
  name: 'Maintenance desk'
};

Never put the service-role key, database password, email key or cron secret in this file. The publishable key is intended for browser use; membership and row-level security protect records.

3. Publish on GitHub Pages

  1. Create a GitHub repository for the app.
  2. Upload the extracted project contents, preserving the docs and supabase folders.
  3. In repository Settings → Pages, choose Deploy from a branch, main, and the /docs folder. Save.
  4. Open the address GitHub provides and sign in with your administrator account.

The website source may be public. Maintenance records stay in the database. Before production use, verify a viewer account cannot edit records and signed-out visitors cannot read them. Do not disable row-level security to fix connection errors.

4. Verify a sender domain

  1. Create an account at Resend.
  2. Add a domain you control, preferably a dedicated sending subdomain. Enter the DNS records Resend gives you and wait for verification. You need access to the domain's DNS settings.
  3. Create an API key restricted to sending from that domain.
  4. Choose a sender such as Maintenance desk <maintenance@yourdomain.com>.

Recipients can use Outlook regardless of the sender. Resend's test sender is restricted; verify a domain before sending to other people. Provider quotas and pricing depend on your account.

5. Deploy the email function

From the project folder, use the Supabase CLI (Node.js/npm required):

npx supabase login
npx supabase functions deploy daily-reminders --project-ref YOUR-PROJECT-REF

The supplied config disables gateway user-JWT checks for this cron endpoint. The function instead requires a private x-cron-secret on every request. Keep that authentication check.

In Supabase → Edge Functions → Secrets, add:

  • RESEND_API_KEY: private sending key.
  • EMAIL_FROM: your verified sender, including name/address.
  • CRON_SECRET: a long random secret (at least 32 random bytes, generated securely).
  • APP_URL: the published GitHub Pages address.

Supabase provides SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY inside the hosted function. All private keys remain server-side. Never commit them to GitHub.

If you change planning rules, run node sync-planning.js before redeploying, so browser and email calculations stay identical.

6. Activate the morning check

  1. Enable pg_cron and pg_net under Supabase Database → Extensions.
  2. In Supabase Vault, create maintenance_function_url with the value https://YOUR-PROJECT.supabase.co/functions/v1/daily-reminders.
  3. Create maintenance_cron_secret in Vault. Its value must exactly match the function's CRON_SECRET.
  4. Run supabase/schedule.sql once. It checks every five minutes; your saved timezone and morning time control when emails become due.

To remove the scheduler:

select cron.unschedule('maintenance-daily-check');

You can also pause emails from Email reminders in the app. Check Cron history, function logs and Email activity for failures. Scheduled time is not a guaranteed inbox delivery time.

7. Enter data and test delivery

  1. Add machines and parts, including physical on-hand spare quantities.
  2. Add components with matching PNs, quantity per change, last replacement and calendar-day interval. An inspection due date overrides the next replacement date.
  3. Add open purchase orders. Use Receive for partial or final receipts: it adds stock.
  4. Use Complete after maintenance: it consumes stock and starts the next interval.
  5. In Email reminders, add your own address first. Select summary, purchasing alerts, or both. Review the email preview.
  6. Set timezone and morning time. Enable emails only after the backend and sender are connected. Confirm Accepted in Email activity and check your actual inbox.
  7. Add the selected recipients. Each can follow all machines or one machine, and can be paused individually.

Receiving historical orders also adds stock. Reconcile opening stock to avoid counting those deliveries twice. Leave emails paused until the records are correct.

Verification and limits

The package includes automated planning and simulated-email tests. No real emails were sent. Live Supabase permissions, database functions, scheduled runs, DNS verification, actual inbox delivery and browser appearance must still be verified after deployment.

The forecast spans two years. It uses replacement intervals and inspection dates, not sensor-based failure prediction. Shared parts pool demand across machines. Late open orders are flagged and excluded from expected coverage. Completion and receipt history is retained.
